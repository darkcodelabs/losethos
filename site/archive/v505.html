The LoseThos IBM PC Operating System
x86_64, preemptive multitasking, multicore, open source
LoseThos is simple.  It runs on a standard 64-bit PC, nothing exotic, and runs native x86_64
code.  It's purpose is for users to have fun programming.  Nervous about no memory
protections?  You'd freak if you knew how many embedded devices operate just fine with no
protections.  Don't write programs that malfunction.  At the worst, you reboot.  Takes 2 seconds.

I come from an embedded systems background.  In our school we were graded on a curve
based on code size.  It's 2.5 Meg and 100,000 lines of code, but I can bloat it if you'd like that
better.  It's small through strategic thinking, not tactical.

It's a live CD so you can test drive or install.

Lite version includes:
  • 64-bit x86 Kernel with Multicore support.
  • 64-bit Compiler/Assembler (Yes, wrote it myself.  Compiler, not interpreter.)
  • Source files and the command line window can have graphics, links, icons, trees, colors,
    margins -- everything is seamless and uncluttered.  No resource, object or executable files.
  • 64-bit pointers.  All tasks on all cores run with physical address map with full access to all
    locations at all times.  On my 12 Gig machine, all tasks can access all 12 Gig of RAM!  
    Most other operating systems have a 4 Gig limit per task.
  • Highest CPU privileged mode at all times.  No off-limits instructions. No mode changing
    penalties.  What?  You need a nanny?
  • Switches tasks in half a microsecond.
  • CD/DVD reading and writing, ISO9660 file system
  • 640x480 16 Color VGA Graphics
  • Boot loaders for CD-ROM or hard disk
  • Keyboards & Mice
  • Hard Drive, Support for FAT32 and LoseThos native file systems, File compression
  • Graphics Library
  • Tools/Utilities including profiler
  • Demos and Documentation
  • Games
  • Bible and hymns
  • All source code included... Seriously!  Including my 64-bit compiler!  It only compiles
    natively, with my compiler.  You can't use gcc.  Instead, boot LoseThos and compile
    everything.

LoseThos never executes code not written by me except a couple BIOS config calls.  It's
100,000 lines of public domain code with no GPL restrictions, written by me over the last 6
years, full-time.  It was written completely from scratch with no code as a starting point.

Strategical decisions that made it small and simple:
Low line count and simplicity are the goal, with it small enough for someone to get their head
around and having it unintimidating.  That's one reason, I'm thinking of doing all the
programming myself -- not accepting contributions of code -- and limiting my ambitions for
LoseThos hardware and featurewise.

Small resource use is not really a goal.  You don't get a cookie for reducing a 64-bit machines
RAM below 512 Meg.  I can run it on 32 Meg or less, but who cares.  I can delete the Bible
and cut the install size, too.  Low user program line count is the ultimate goal.  "Hello world"
takes 1 line and drawing a line on the screen can be done in two lines.  My vision comes from
my remembering my Commodore 64.  Back then, practically all computer users programmed
and tinkered.  Programs were in magazines.  I had a book which literally told what every
address location was used for.  Linux is intimidating.

  • 640x480 16 colors.  Period.  Forever.
  • No Security.  Everything running in highest privilege level.  No networking.
  • Pure 64-bit.  No legacy support.
  • Update whole screen at 60 Hz -- don't mess with rectangles telling what's changed.  It's
    optimized for full screen games where keeping track of invalid rectangles does not help.
  • All intermediate values in compiler are extended to 64-bit when fetched and only 64-bit
    computations are done intermediately.  No type-checking.
  • One editor/word processor/browser thing for command-line, source code,
    documentation browser, dialog forms, everything.
  • One Font, 8x8.
  • No child windows.  One window per task.  Buttons and stuff are widgets, not child
    windows.
  • Threads = processes = tasks, no distinction
  • One memory map for everybody -- virtual set equal to physical.
  • One language and compiler for command-line scripts and code.
  • No object files.  Whole files are processed almost exclusively, allowing for compression.
  • All tasks have a heap and a symbol table.  Think of the scope as that of environment
    variables in other operating systems.  As text is typed at the command line or you run
    programs by #including them.  The symbols go in the table.  If a symbol is not found, the
    parent task is checked.  The father of all tasks has most symbols you need waiting in it's
    table.  No need to #include headers.  No need for namespaces -- scoping occurs
    automatically.

Promises:
  • LoseThos will always run everything in kernel mode, ring 0.  There is no user mode.  All
    programs will have full access to memory, I/O ports, instructions, etc.  Yes, this means
    you can crash LoseThos very easily.  Yes, this means no security.
  • LoseThos will always "identity map" virtual memory.  (Virtual addresses are the same
    as physical.)
  • LoseThos will never have full networking support with an Internet browser, etc.
  • LoseThos will always have one video mode, 640x480 by 16 colors, unless this mode
    might become unavailable on computers in the future.  You can assume the screen will
    be the same for everybody.  There's plenty of CPU for very little screen to update -- only
    1/37th the power needed for a 1600x1200x24 bit mode.
  • The LoseThos operating system will be free, but I might sell applications or support, or
    possibly do adware.
  • LoseThos will be 100% open source with all source included, unless device drivers or
    something can only be included with non-disclosure agreements.
  • All function args and returns will be 64-bit -- no plans for C++.
  • LoseThos documents are not for printing -- they're dynamic and intended for the
    screen.  There will always be just one font, a fixed-width font, and I do not have plans for
    Unicode, just ASCII.
  • LoseThos is not for multimedia.  Games will be created by programmers, not artists --
    calculated sounds and images.  Who has time to twiddle pixels all day and who has
    voice actors and owns a 1930's radio show recording studio!

Not Promised:
  • LoseThos is subject to change and backward compatibility is NOT guaranteed,
    however, changes are a pain for me, too.  It's mostly done.  You are far safer working
    with MAlloc compilation than static binaries because I can add members to classes,
    reorder members in classes, add default args to existing functions, change #define
    values, etc. all without breaking Compatibility.

Answers to FAQ:
  • LoseThos has just a compiler, not an interpreter.  It can compile a statement or function
    right into a chunk of memory ready to execute.
  • LoseThos refreshes the whole screen at 60Hz.  What's the worst case for a graphics
    library?  Full screen updates, right?  I optimized for full screen updates instead of
    messing around with which rectangles have or have not changed.
  • LoseThos has no networking.  You can unplug your network, if you like.
  • Signed integers are I0, I1, I2, I4 and I8.  Unsigned integers are U0, U1, U2, U4 and U8.  
    Floats are F8.
  • When threatened over FAT patents, I made my own file system.  I tried to do nothing
    which could get me sued.  I can think of no technique besides a FAT table that's decent,
    so I went with contiguous files which can't be grown.  I'm not interested in multimedia,
    anyway, and my whole personal partition never exceeds about 64 Meg.  Any one file is
    small.   LoseThos is geared toward whole file reads and writes.  This sucks but
    simplifies everything and allows for compression and checksums.  If you reserve space
    when a file is created, you can do direct block access relative to files for the ultimate in
    performance.  The dictionary is accessed this way.  Logging is a pain -- you have to
    buffer in memory and write-out the whole thing.  Buffering text is easy with the Ltf
    document framework.  Since FAT support might be removed, I do not count on growing
    files.
  • An ISA bus access, IN or OUT instruction, is a fixed-time of around 1.6 microseconds
    and can be used for delays.
  • LoseThos is for programmers.  Multimedia in games is a frustration for programmers.  
    HD Audio sounds are made by calculating waveforms -- it's funner than voice actors
    and a 1930's radio sound effects studio.
  • You must burn an ISO image of the LoseThos CD and boot to it if you wish to compile.  
    LoseThos has it's own compiler that I wrote.  It's syntax is nonstandard C/C++.  It has
    most of C's language features, a little of C++ and brand new stuff not seen elsewhere.
  • The Windows DLL files on the full version are just to run the LTZ program, which will
    uncompress LoseThos files from Windows.  AT NO TIME DOES LOSTHOS RUN
    OTHER PEOPLE's CODE except a few BIOS config routines.
  • It really is 64-bit mode.  The segment registers, FS, and GS, in 64-bit mode can
    function as additional general purpose registers, with some work.  I keep the FS
    register pointing at the current task record and the GS register pointed at the current
    mutlicore CPU record.
  • When disassembling 64-bit code, there are many instructions which appear to be 32-bit
    instructions.  XOR EAX,EAX will clear the upper 32-bits and is a byte shorter than a
    true XOR RAX,RAX.
  • All tasks, regardless of what they're doing or not doing are in a circular doubly-linked
    list.  The scheduler spends it's time circling, swapping-in the next task after checking if
    the next task is asleep or waiting for a message that hasn't arrived, in which case it
    skips it.  It uses the RDTSC instruction for times, so resolution is great.  When a task
    does I/O, it gets swapped-in, checks what it's waiting for and voluntarily swaps out and
    the next in the circle is swapped-in.  That's called cooperative multitasking.  There is an
    timer interrupt running 2kHz that interrupts any task that might not be cooperating and
    swaps it out, and swaps in the next, unless the task said "Do not preempt me".  Polling
    devices instead of using interrupts eliminates a ton of compatibility nightmares.  Sure,
    it's easy to get interrupts running on one machine, but when you have to worry about
    shared interrupts and stuff, you have to enumerate all devices!  All or nothing!  The swap
    operation just involves saving registers to the task record and restoring the registers of
    the next -- no memory map fiddling or virtual memory disk activity, so a swap only takes
    a half a microsecond.  The order of the tasks in the queue determines which windows
    are in front of which others and which window is on top.  The RDTSC frequency is
    measured continuously with HPET as a reference and a sleep delay can be calculated
    from that measurement.  Using HPET itself would be better since both RDTSC and
    HPET are quick operations, but I don't know if HPET is present on all systems.  It
    probably is on 64-bit systems and I should assume that.
