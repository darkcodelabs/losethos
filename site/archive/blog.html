When I was taught asm programming, the rule of thumb was to count memory 
referrences.  The instruction fetch would be a memory referrence and any 
nonregister data was a memory referrence.  These days it's probably cache 
misses.  It's a strange world, if you're old school and haven't stayed current.

When I planned LoseThos, I wanted to be aggressive for performance by not using 
paged memory and only using ring 0.  If you think about paging and count memory 
references, you come-up with 5 times the nonpaging number!  Obviously, it can't 
be that bad, but how can it not be worse?  It turns-out that with silicon, they 
largely negate the penalty, but not completely, obviously.  LoseThos is higher 
performance than everybody else because it identity-maps memory (doesn't mess 
with paging) and never switches out of ring 0.

don't seem right.  The CPU converts instructions from CISC to RISC and optimally 
schedules the mini operations.  It does operations out of order and in parallel. 
 Many instructions are free!  Caching is hard to follow.  Instruction timings

Someone was squacking about the BTS vs the OR instructions over on OSDev.ORG.

compiler uses BTS when possible.

Shift operations will always be a little faster than MUL and DIV, but not by 
much.  That gap has closed, largely.

The funny thing about the CISC to RISC conversion I discovered when I did my

write a compiler and it would be almost as fast as gcc because the CPU does

My heap routines have a huge overhead per allocation.  Speed was the only 
consideration, and I guess, simplicity.  There's a nifty routine you can call, 
MSize() which returns the true size of a heap allocated object, so you can 
determine how much over-allocation was done or if you have amnesia.

It's wonderful what you can do when you exercise strict control over your tool 
chain.  My MAlloc() routines take a second parameter telling which task's heap 
to use or even an independant HeapCtrl() can be specified.  You can, then, fetch 
the size with MSize() or you can alloc a clone with MAllocIdentical().  MAlloc() 
requires a task parameter, usually NULL to indicate current task, but Free() 
doesn't require the task because it's stored in the header located in the bytes 
before along with the size.  The heap routines have multicore and multitasking 
safe locking and all tasks are on the same address map, so you can freely 
MAlloc() and Free() from any task off of any other task's heap.

I exercise control with the compiler, too -- all subroutines must create an RBP 
stack frame because the Caller() routine is used for stack tracing.  In the 
wallpaper, a stack trace is done every second or so, so all tasks must maintain 
a valid, stack tracable stack.

Registers are under strict control, too.  The compiler does not preserve about 5 
registers and the FS and GS registers are used for current TaskStruct and 
current CPUStruct respectively.  Code, simply has to follow these rules in 
LoseThos.

LoseThos has no linker and no OBJ files -- it doesn't need them.  The compiler 
calls MAlloc() and places code, ready-to-run, right into memory.  It adds 
symbols to a task's symbol table and it searches the symbol table to resolve 
symbols when call statements are compiled.  The compiler can produce flat BIN 
files but you don't need to do that unless you work on OSMain or the Compiler 
module.

When the system boots, the boot task is called "Adam", as in Adam-and-Eve.  All 
tasks have a symbol table and child tasks will search the parents' table when 
symbols are not found.  So, Adam's table holds globally defined symbols.  When 
Adam is initialized during boot, he compiles lots of APZ, adam files, that are 
just like CPZ file.  You might need a file to be in Adam's space if it is meant 
to be immortal or system-wide.  All tasks share the same address space, but 
Adam's heap is guarenteed never to be freed because Adam never dies.  Adam's 
symbols are global, too.

During boot, the Adam1.APZ is like AUTOEXEC.BAT.  It includes header files for 
the kernel, OSMain, and the Compiler modules, then includes Adam2.APZ which 
compiles libraries into memory and finishes with Adam3.APZ which is for user 
account files.  If a file is not found in a user account directory, the parent 
directory is searched.  This allows default account files to work.

There is no PATH in LoseThos.  It's closer to the way a Commodore 64 or Apple II 
worked -- code you enter at the command line is either executed immediately or 
is compiled into memory, ready to run.  And, you never #include header files 
because all the library symbols are already waiting in Adam's symbol table and 
executable code is waiting in Adam's heap.

LoseThos identity maps virtual to physical memory.  This and ring-zero-only, are 
the most core attributes of LoseThos.  Originally, I thought eliminating the 
4-levels of look-up for each address access under paging would be much faster.  
I didn't realize clever silicon largely eliminates the penalty you would expect

but saving a task context and loading a context, it can do 3,000,000 per second. 
 You can read about and download my OS from 2004 at the Internet Archive.  (It's 
a slow link, so wait a minute for it.)  That version used TASM to create a DOS

(identity mapped, actually, because 64-bit mode requires paging), don't be

impossible for you is not impossible for me.

There is no "make" utility in LoseThos.  You simply #include all the files like 
::/LT/OSMain/OS.SPZ or ::/LT/Compiler/Compiler.SPZ or ::/LT/Adam/Adam2.APZ.  
Don't worry -- my compiler is very fast and there are only 131,589 lines of 
code, total.  I wrote every line over 8.6 years and don't forsee getting help.

I wonder if there is a name for this phenomena -- if you can keep things small, 
they can collapse in on themselves and become even smaller.  You don't need a 
linker, if it is small.  If you wanted, you could somehow use 16-bit pointers if 
your data was small and the pointers would make it even smaller.

My compiler will make binary files, but you're supposed to do JIT, normally.  
There is no linker in LoseThos, but binary files can import and export symbols 
when loaded into memory -- basically linking.  Everything is trivial because all 
tasks use the same address map -- virtual identity mapped to physical.  I place 
all code in the lowest 2 Gig so all asm CALL instructions are REL32 address mode 
 (Don't worry it's 64-bit).  Code gets placed below 0x7FFFFFFF and works 
backward.  There is no concept of kernel or user because all is ring-zero.  When 
the loader or JIT compiler is placing code into memory, it calls MAlloc() and 
allocates from the code heap.

Memory is associated with certain tasks, so it is freed if the task dies.  
"Adam" is the first task and he is special because he never dies.  His memory is 
like kernel memory in other operating systems.  At boot, Adam #includes 
::/LT/OSMain/Adam1.APZ which is basically like an AUTOEXEC.BAT file. 47,000 
lines of code are compiled into Adam's memory and his symbol table is populated. 
 Task symbol tables are like other operating systems' environment variables, in 
terms of scope.  Children of Adam will search Adam's table if they do not find a 
symbol in their symbol table, so Adam is for global symbols.  Here is the 
Symbol Table.  Notice the addresses around 0x7FFFFFFF.  The addresses below 
0x100000 are the OSMain module, loaded by the boot loader in real mode before it 
switches to 32-bit, then 64-bit modes in ::/LT/OSMain/OSStartUp.CPZ.

JIT compilation is trivial -- easier than making object files and linking.  You 
call MAlloc() and put the compiled output in that chunk of memory and simply 
look-up all the symbols from the symbol table and patch them immediately!  You 
never need to #include headers when running in JIT mode because Adam's symbols 
get searched if it is not found locally in the task's table.

Stacks are 256K allocated when the task is created from the pool of memory above 
0x7FFFFFFF.  You must keep fixed-size stack in mind and adapt by using heap 
instead, for big items.  This is probably the biggest drawback with LoseThos.  
For string operations, I always check the length I need and dynamically allocate 
the string object, so I never have overflows even though I use StrCpy() and 
StrCat(), etc.
