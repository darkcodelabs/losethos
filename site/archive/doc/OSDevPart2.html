Writing a PC Operating System, Part 2

                                       by

                                  Terry Davis

                               Author of LoseThos


Instead of rehashing info which can be found in OSDev tutorials and wiki's 
elsewhere, I'll share only what hasn't been said.  For the most part, developing 
an operating system is reading datasheets for hardware and getting devices to 
work using lots of trial and error.  You would think trial and error, with 
persistence, would be obvious but an incredible number of the people who show-up 
at www.osdev.org type something in and expect it to work the first time.  Here's 
how to program hardware:

1) Get a datasheet.  Intel is great.  Most hardware has no available datasheet, 
however.  (I don't support most hardware.)  Go to Linux source code if you 
really have to, but realize you will be bound by GPL if you do.

2) Find at what ports or memory addresses the device should be located.  There 
are sites which describe most PC I/O ports.  Window's system information can 
help.  I/O ports are mostly first generation PC hardware, the modern stuff uses 
memory mapped registers, more.

3) Probe hardware until you get a sign of life at the address.  It's mostly old 
hardware that's at fixed addresses.

4) Try to take baby steps until you get it working.  Unfortunately, modern 
hardware often requires big steps at certain places.  There's always a bit some 
where you need to set before it will work.

5) When you get stumped, don't stand still, try anything no matter how crazy -- 
you'll learn bits and pieces that give you a full picture.  You'd think this 
would be obvious, but often you have to write disposable test/debug code.  I 
have no respect for anyone who won't go a little out of their way to write a 
routine to do a hex dump or register dump.  Frankly, if you can't figure-out 
stuff on your own, you're probably not qualified.  Tenacity is what's required 
-- whole days spent learning you need to set a bit.



I've got some depressing news.  As author of the top-listed alternative 
operating system according to a Google search of "64-bit operating system", I 
speak with some authority. (I also have a 50 member Facebook group.)  You have 
four choices on supporting hardware:

1) Pick a (few) hardware platforms (what you have physical access to) and write 
drivers for just those.  This is more or less what Apple did -- limited, 
specific hardware.

2) Attempt to use Windows or Linux drivers?  Forget it.

3) Get other people to write drivers?  You're delusional.
 
4) Support just common hardware, the LoseThos approach.  

Depressing.  Why do you think there's Linux and no others?  You can see lists of 
hundreds of abandoned operating systems.

Once you start developing graphics, immediately try a full-screen 30 
frame-per-second test to see if that resolution and color depth is feasible.  
There are many unviable hobby operating systems with graphics that are too 
ambitious.  Without hardware acceleration, it's slow and to get hardware 
acceleration, you have to support many different graphics cards... which brings 
you to the delema I just discussed above.

Finally, good luck with PCI interrupts.  I'm baffled on how you assign 
interrupts and cope with sharing.  It seems like you must support all devices on 
each system in case they share, so supporting just some hardware might not work. 
 Sure, it's easy to do interrupts for your own system, but it sounds hard to do 
it for any system.  I avoid using hard-drive interrupts because polling is okay 
and by not using interrupts one less thing can fail on other systems.
