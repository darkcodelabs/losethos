Wisdom

* Writing your own code is more fun then modifying someone else's.  I've decided 
I enjoy programming most when I know what I'm doing.  Sadly, I've heard that 90% 
of programmers work on maintaining code.  One good thing about looking at other 
people's code, though, is you learn what to and what NOT to do.  

* Use a profiler.  Profiler  Don't make noncritical code optimized.  Such 
optimizations are ugly, complicated and bulky.  They create a maintenance 
burden.  Stay agile.  Obviously, develop good habits for all code, though.

* When I was inexperienced, I remember coming across different code indentation 
and formatting schemes.  I couldn't read, being too distracted.  Over the years, 
I've become less bothered by variations.  I'm not alone.  I remember one young 
coworker who reformatted a program I had written when he was asked to work on 
it.  Then, he asked me for help!  Code can become your baby.  Caring is probably 
good.  In later years, I remember working on ugly code... I just wanted out of 
there.

* Misspellings almost never make things unreadable, but they definitely 
distract.  There was an interesting study where people were presented with a 
paragraph containing completely misspelled words except for the first and last 
letters.  It was still readable!  Generally speaking, people use spelling as an 
IQ test and you'll lose your reader's attention.  The same is true in oration.  
It's silly, but the distractions presented are a serious problem.  If a 
politician bumbles a word, the audience won't hear the next 30 seconds because 
they're flustered.  Another reason for standard forms is to make things machine 
readable.

* Off topic, I took a control system's course and our book used different 
letters for matrices than I was used to.  I couldn't adapt.  That sounds silly, 
but imagine d=g(u) instead y=f(x) everywhere.  I realize I'm guilty of changing 
things with LoseThos, but had I followed standards, LoseThos would be nothing 
but an inferior imitation of Linux.  Instead, it's and improvement.  You can't 
tell me the standard library routines, getchar, scanf, gets are good the way 
they are.  getchar() requires a carriage return.  scanf() is bizarre.  gets() 
has length problems.
 
* When working on other people's code, people tend to be defensive.  They use 
caution when uncertain.  This adds unnecessary code.  This is just a fact of 
life.

* Documentation which is out-of-date is worse than no documentation.  I tried to 
keep documentation right by code in LoseThos.

* There is potential for huge added functionality by enhancing low level 
routines.  Imagine modifying a date range prompting routine like A2LTDate(), 
file choosing dialog, or A2I() or PrintF().  Imagine modifying the compiler's 
preprocessor, Lex(), making new #cmd operations.

* Often, you're faced with not being able to fully implement a feature.  
Professional companies choose not to include a feature if it can't work 100%.  
Half-baked features tends to frustrate users.
 
* Not all features are good to use.  I've seen cases where people use macro 
functions (#define) to make C code look like C++ code.  This is one more layer 
you have to look-up to understand.  An advantage of nonvertical coding is 
readability.  Reducing redundancy is good, but it is possible to get carried 
away with nonstandard library routines.

* One mentor discouraged using abbreviations.  One advantage of nonabreviated 
labels is there's no uncertainty on how to spell them.  Typing is never what 
slows you down, except maybe at the cmd line.  Uncertainty is what slows you 
down.  Forgive me if I've used obscure abbreviations.

* One mentor always put "temp" on the beginning of local vars -- "tempd" instead 
of just "d".  The reason is probably for text finds and replaces.  I've somewhat 
eliminated this need with the "whole label" search feature.

* Grep() is my best friend.  I use a wrapper function F().

* It's easier to write a cmd line interface than a GUI one.  If you are working 
on something for personal use, why not?

* On a modern home computer, the only things which take significant memory are 
disk cache, graphics and sound data.  Code related items do not.  If you have 
10-20 bytes of machine code for each line of C/C++ code, a million lines of src 
code takes 20 Meg.  If you have a million lines of code and store an 8-byte 
value telling where each line is located, that's 8 Meg.  I have 12 Gig of RAM! 
That would be 0.07%.  The compiler-generated debug structures that LoseThos uses 
do not use significant resources.

* A home computer doesn't need a big disk cache.  How often do you listen to the 
same multimedia item more than once?  If you have a database server, you need 
disk cache.

* Run toward bugs not away.  Robust code is good in the field, but bad for 
testing--better to have things fail.
