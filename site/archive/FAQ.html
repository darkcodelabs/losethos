  • I have a Dell Corei7 system as my primary system.  It has an extra hard drive where I placed
    3 LoseThos partitions.  Its original hard drive has the factory installed Windows partition and
    a recovery partition which I reformatted as FAT32.  I put the LoseThos master boot loader on
    the extra hard drive and kept the original boot loader on the original drive.  I press the F12
    key when rebooting and use the BIOS to select which hard drive to boot from.  I make
    snapshots (just copies) of my primary LoseThos partition onto the other 2 partitions on the
    extra drive and onto the FAT32 partition on the Window's drive.  When I render my primary
    LoseThos partition unbootible, I boot to a backup LoseThos partition and fix it.  When
    working in Windows, I use the FAT32 partition on the Window's drive for transferring files
    between LoseThos and Windows or vice-versa.

  • The LoseThos document file format used for source files, contains a roughly ASCII portion, a
    terminating zero, and a binary graphics portion.  The documents contains links, graphics,
    formating commands and trees widgets, etc. placed between dollar signs in the ASCII
    portion.  ASCII 5 and 31 are used for the current cursor location in the file and a "shift-
    space".  If the filename ends in "Z", it is stored compressed with the Losethos compression
    format.  The compiler and all the tools recognize this format.
  • The Fs and Gs segment registers are used like general purpose registers, holding the
    current task record address and cpu record address, respectively.  In 64-bit mode, you set
    the segment base addresses with a model specific register.
           MOV        RDX,RAX
            SHR         RDX,32
            MOV        ECX,IA32_FS_BASE
            WRMSR
    To access the task or cpu structure, I have to use a trick.  I place the record's address at
    offset zero in the record and get the address like this:
    XOR        RAX,RAX
    MOV       RAX,FS:[RAX]
    This is necessary because [displacement] addressing modes are RIP relative.  (Worthless for
    these segment registers).  This doesn't appear to work:  
    XOR        RAX,RAX
    LEA         RAX,FS:[RAX]
  • Address maps are never switched or modified.  There is, in fact, one map used by all tasks
    on all cores.  Saving a task's context and restoring a new task's context takes less than half a
    microsecond -- no address map changes, let alone disk virtual memory.
  • When you compile a static binary, the compiler prints a few messages.  You can use Silent
    (ON); to supress them.  Compiling OSMain however requires command-line keyboard input
    in the middle of the compile, which doesn't work with Silent(ON);  Umm... you should try to
    avoid making additional static binaries -- that's not how I envisioned it working.
