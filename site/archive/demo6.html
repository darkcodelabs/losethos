LoseThos runs everything in the highest privilege level, (ring 0, kernel).  It allows full access to everything
because it's simpler and boosts performance.  It has no bureaucracy because it's fun.  It's the way it is by
choice because it's fun.  Don't you hate ninnies who harp on the point of overusing an admin account?  Not
having kernel privilege, for a programmer, is like not having an admin password on your own computer!

LoseThos is in no way a Windows or Linux wannabe -- that would be pointless.  LoseThos is not trying to win a
prize for low resource usage or run on pathetic hardware.  Low line count is a goal, though.  It's 100,000 lines of
code including a 64-bit compiler, tools and a graphics library.

A bigger goal is making applications low line count.  "Hello World" takes one line of code.  You can put
graphics on the screen with two lines of code.  You don't need to include header files or mess with
namespaces.  It has a scoping system, though, with tasks inheriting symbols of parents and all system-wide
symbols and code in the Adam (as in Eve) task's heap.  

LoseThos uses some tricks to keep line count down, like processing whole files. It has a flat, identity mapped
virtual-to-physical address map, the same for all tasks.  It updates the whole screen 60 times a second instead
of trying to keep track of what has changed.  The most demanding application is a full screen video game, so it
might as well be optimize for that instead of trying to get idle low.  It uses the same compiler for the command
line as for programs and it uses the same viewer/editor for the command line, help system, forms and dialogs.

LoseThos is not trying to be bullet-proof -- it's for home computers, not mainframes where many users suffer
when a crash occurs.  It reboots in 2 seconds plus BIOS time.  It's no worse than a hung task in Windows or
Linux.  I know people obsess on this topic.  You know how the last 20% of a project takes 80% of the time?  
LoseThos is an order of magnitude simpler by not trying to be bullet-proof.

There are two programmers who will work on LoseThos -- the user and I.  It is for programming as
entertainment, and I mean that.  Why would you buy a 3rd party program to run on a system with crappy
graphics that can crash?  There are no scalablity issues.  Imagine LoseThos more similar in usage to a 8-bit
non-networked home computer's ROM than to Windows or Linux, though, it is 64-bit and far more than that.  
You are free to access anything documented or undocumented in the system source code -- have fun!  I have
fond memories of the days when average users typed-in programs from magazines and tinkered with them.


LoseThos was designed from scratch with a clean slate and has no compatibility with anything else.  Source
code is ASCII plus binary graphics data.  It has a new language roughly based C/C++.  It's more than C and
less than C++ so, maybe, it's C+.  I took every opportunity to improve things once I made a clean break with the
past.  That's another reason LoseThos has value -- it is innovative.

I started with a command line like this:
Dir("*.*");

I added default parameters from C++:
Dir();

I said, "parentheses are stupid."
Dir;

Now, I have a language which looks a little like pascal.  It also doesn't have a main() routine -- any statement
outside a function executes immediately, in order. The command line feeds straight into the compiler (not an
interpreter) and it doesn't have that bullshit errno crap for return values -- command line commands are regular
C+ functions.

Contrary to what you might think, LoseThos is modern.  I wrote a 64-bit compiler and made support for
MultiCore.  Everybody else does SMP which is great if you wish to run two apps at the same time, but what
about one?  Instead, LoseThos does master-slave MultiCore, fully under the programmer's control.

I don't know what everybody else is doing about 32-bit signed displacements, but I'm putting all code in the
lowest 2Gig address range and data above in a 64-bit address space.

LoseThos is primarily for making video games.  It has no networking or Internet support.  As far as I'm
concerned, that would be reinventing the wheel and you can do that instead by dual booting another operating
system.  Similarly, it's not for desktop publishing or multimedia.

When it comes to budgeting, many people buy too much house and find themselves always stressed.  When it
comes to video games, professional companies push the limits and struggle the whole time.  With low
resolution and a modern 64-bit multicore machine, you can write modest games with orders of magnitude less
effort than a professional company with a staff of a hundred.


PROMISES:

1) LoseThos will always run everything in kernel mode.  There is no user mode.  All programs will have full
access to memory, I/O ports, instructions, etc.  Yes, this means you can crash LoseThos very easily.  Yes, this
means no security.

2) LoseThos will always "identity map" virtual memory.  (Virtual addresses are the same as physical.)

3) LoseThos will never have full networking support with an Internet browser, etc.

4) LoseThos will always have one video mode, 640x480 by 16 colors, unless this mode might become
unavailable on computers in the future.  You can assume the screen will be the same for everybody.  There's
plenty of CPU for very little screen to update -- only 1/37th the power needed for a 1600x1200x24 bit mode.

5) The LoseThos operating system will be free, but I might sell applications or support, or possibly do adware.

6) LoseThos will be 100% open source with all source included, unless device drivers or something can only be
included with non-disclosure agreements.

7) All function args and returns will be 64-bit -- no plans for C++.

8)  LoseThos documents are not for printing -- they're dynamic and intended for the screen.  There will always
be just one font, a fixed-width font, and I do not have plans for Unicode, just ASCII.

9) LoseThos is not for multimedia.  Games will be created by programmers, not artists -- calculated sounds
and images.  Who has time to twiddle pixels all day or who owns a 1930's radio show recording studio!


Not Promised:

1) LoseThos is subject to change and backward compatibility is NOT guaranteed, however, changes are a
pain for me, too.  It's mostly done.  You are far safer working with MAlloc compilation than static binaries
because I can add members to classes, reorder members in classes, add default args to existing functions,
change #define values, etc. all without breaking compatibility.




Frequently Asked Questions:
  • LoseThos has no networking, cannot call home.  Unplug your network if you wish.
  • Files are compressed, not encrypted.  To uncompress use the LTZ Windows or Linux programs or, if in
    LoseThos, just copy to a filename not ending in Z.
  • It depends on no outside code.  The /Windows and /Linux directories contains a uncompress utility that can run
    from other operating systems.
  • I8 is 8 bytes (64-bits).  It's for x86-64, not ARM or whatever.
  • Fs is the x86 FS segment register, not "file system".
  • I wrote my own nonstandard assembler.  Trust me, it runs on x86-64 -- the appearance of the assembly language
    doesn't matter -- the machine code bytes generated by the assembler matter.  
  • A public domain license is permissive license meaning you can do anything with it. GPL  is a restrictive license.  
    There is no GPL, BSD, or GNU code in LoseThos.
  • Adam as in Adam and Eve, the father of all tasks.  (Don't worry -- I'm an evolutionist.)
  • Bt(), Bts() and Btr() are bit operations named after the x86 instructions, not "bit torrent".
  • Sleep() is nothing to do with power saving mode.  It makes a task wait a certain number of milliseconds
  • Refresh is the rate the video memory is updated.  It's a software, not hardware, thing.
  • BIOS? LoseThos requires no changes to firmware -- it's an ordinary conventional hard-drive (or live CD-ROM)
    operating system.  It does not use the BIOS after it boots.  Ask not why it boots in 2 seconds, ask what the heck
    other operating systems are doing.
  • Swaps/s is the number of task switches.  LoseThos can save registers of one task and load registers of another in
    half a microsecond.  LoseThos' tasks do not have virtual memory, so there is no disk activity involved.  It doesn't
    have to shuffle memory registers around, either, because all tasks use a single address map.  2,000,000 swaps a
    second are possible.
  • HMapRep() will show a sorted list of functions by address.  The compiler calls MAlloc() for space to store code
    and functions go all over, unintentionally.  HFunsRep() will sort by function name.  HAllRep() shows all symbols.  
    Call LtfMax() to increase the command-line buffer before using those.
  • I work on LoseThos full-time.  I wrote every one of the 100,000 lines of code, a 64-bit compiler, kernel, graphic and
    standard libraries, misc tools, songs, demos and documentation.  There is no linkage or usage of any code not
    written by me.  I've been at work for 5 years.  Do the math -- 20,000 LOC a year.  I took courses on compilers,
    computer graphics, supercomputing, embedded system design, and operating systems in school.  I worked on
    Ticketmaster's proprietary VAX operating system.  I've have tons of experience programming in assembly
    language on embedded systems.  LoseThos is more like an embedded kernel then a mainframe kernel.  These
    sites were used to make LoseThos.
  • REX is a x86_64 instruction prefix which provides access to the extra 8 registers available only in 64-bit mode.
  • HAL is not used.  LoseThos runs on bare metal hardware.  No BSD, GNU or GPL code either -- 100% from
    scratch.
  • I make my demo video's with a BMP file screen capture task taking 8 frames a second.  I don't know if it requires a
    license to save BMP files, so it's not on the distribution.  Write your own BMP support.  I dual boot with Windows
    and use a FAT32 partition to transfer my BMP and SND files to Windows where I use Window's Movie Maker to
    make movies.
  • LoseThos does not use CTRL-Z for file terminators.  It places a zero byte after the ASCII portion of a document,
    before the binary (graphic) data.
  • Does an operating system that crashes if you create a bug in your program seem mockworthy?  LoseThos reboots
    faster than you can kill a task in a Windows IDE.  Who's the fool?
  • Does polling disk activity seem mockworthy?  Ever heard of cooperative multitasking?  If you haven't you're
    mockworthy.  I chose not to use interrupts (on just disk I/O) because they unnecessarily add a little complexity and
    create more issues for conflicts and incompatibilities.  
  • You can do what you like with the songs on LoseThos.  I wrote them, enjoy.  Write hymns of praise to God if you
    know what's good for you.
  • The songs a stored as C+ programs which call Play(""); and pass it strings like "qA#eCC" for quarter-note A
    sharp, two eighth note C's.  They're all only 1000 bytes or so.
  • The bulk of the 18.9 Meg is taken by a dictionary.  The Bible and a Windows application for uncompressing from
    Windows take-up a sizable chunk.  The operating system, compiler, tools, documentation, demo's with all source
    code is only around 2.2 Meg.
  • There are no magic files-as-directories or hidden files of any type.  LoseThos allows graphics in source code files,
    so there are no resource files.  It compiles source just-in-time so there are no object or executables.  It has
    automatic file compression on a file-by-file basis, so files are tiny.
  • The source line information is available for pretty-much all code.  LoseThos loads map files telling where source
    code symbols originate for the two static modules.  (Static modules are not just-in time -- the kernel and compiler
    are static modules, about 40,000 LOC.).  For the code compiled during booting, the other half of LoseThos --
    40,000 LOC, the compiler retains source line info.  The document format supports a type of link which searches
    the symbol table and goes to the source code.  Therefore, it's really easy to place links in source code to other
    code.  Remember, LoseThos source file documents are not just text -- they support graphics and links and trees
    and more.
  • Been trying to tell you LoseThos is revolutionary.  Where else can you get graphics in source code and
    links, etc.  It would be a waste of time if it weren't different!  There is no GNU or GPL code -- the compiler
    and kernel are 100% original, started from a clean slate, not stuck in the 1970's with ASCII only source files.
  • LoseThos has a feature I created that I've never heard-of elsewhere.  You can turn-off preemption while keeping
    interrupts on.  The timer interrupt just agrees to swap-in the same task.  Effectively, it's like placing a lower priority
    on timer interrupts, if you think about it -- you still get nontimer interrupts with preemption off.  Used too much,
    though, preempt-off is bad because the timer interrupt is, like, canceled, not postponed.  You'll probably have to
    think about this to understand what I mean.  This feature is okay, but doesn't do much for LoseThos since there
    are very few other interrupts happening that benefit.
  • There is no layering or structuring in LoseThos -- everything, including all user programs, run in kernel mode.  The
    OSMain module is the closest thing to a kernel, but it is delimited by being enough to switch to 64-bit and load-in
    the remainder of the operating system with debug routines for convenience.  OSMain is loaded by the boot loader
    while in 16-bit mode, so it's size is limited to around 400k.  There is little redundancy in LoseThos, so most of the
    disk and file system code goes in OSMain.  I show restraint on OSMain because some day I might want to put
    USB support into OSMain so it could boot from a memory stick and the USB code would be sizable.
  • OSMain loads-in OSMain2, the compiler.  Together these are 40,000 LOC and are the only portions of LoseThos
    stored as precompiled binaries.  The remainder of the operating system is compiled from source and placed into
    memory during boot, another 40,000 LOC that compile in less than 2 seconds.  A syntax error in source compiled
    during boot would render it unbootable, so, I included enough in OSMain and OSMain2 to edit a start-up source
    file, so you might fix a problem.
  • The song melodies were randomly generated, but the lyrics were by me.
  • There really aren't fprintf(), fscanf(), ReadLine(), WriteLine(), etc.  text file routines.  Instead, you load whole
    document files into memory with LtfRead() and read or write to the document in memory and save it with
    LtfWrite().  This is simpler in some ways and handles the issue of graphics that can be included in LoseThos
    documents.  For performance, you can use FRBlks() or FWBlks() which access disk blocks in a file directly.
  • The LoseThos distribution used to be 32 Meg.  I realized I could compress the dictionary file, so now it's 18 Meg
    and it uncompresses when you boot the first time.
  • LoseThos used to have a feature where you could substitute pictures for words, PicWords.  It replaced
    "LoseThos" with a logo.  It was a dumb feature because the pictures could only be one character high, so I
    removed it.  It had a minor impact on performance and was bloat.
  • LoseThos maps 128 Gig of virtual memory to handle computers far into the future with lots of RAM.  I have 2 Gig
    of RAM.  It's simpler just to map it, instead of trying to figure out how much there is.  It makes it a known quantity,
    also, making memory layout a little more standard for fixed-address items.  There is no disk virtual memory
    swapping in LoseThos.
  • WordStat collects statistic on all text files (source, documents, but not dictionary or Bible) just after booting.  
    Takes 5 seconds and has the benefit of loading everything into cache.  Happens in the background.  WordStat is
    an simple predictor of the next word based on statistics of what words most often followed what other words.
  • LoseThos renders text as graphics using a font.  VGA has no capability to have a text and a graphic layer, so how
    did you think it mixed text and graphics or scrolling text?  There is a way to trigger LoseThos to operate text mode.  
    I made this as a fall-back if switching to 640x480x16 color VGA failed.  Just return a false return code from the int
    0x10 BIOS call in OSStartUp.ASZ.  You can do limited things with only text, but it will function.  I purposely kept
    things like the font the same, so I didn't needlessly cause incompatibilities with text-only mode.
  • Someone's complaining about ASM code.  Ba Ha!  I hate to tell you but instructions like LGDT and the ability to
    specify registers to save during a context switch can only be done in assembly.  I kept the minimum assembly
    possible, but there are places where you can't avoid it.
  • LoseThos only assembles or compiles natively.  You cannot compile LoseThos code outside of LoseThos because
    the language is different and nobody has written a compiler/assembler for my language on another platform.  For
    example... I saw that it was stupid to have parentheses on C/C++ function calls having no parameters, so I
    eliminated them.  That part looks a little like PASCAL but LoseThos C+ is definitely a flavor of C/C++ and not
    another language.
  • Everything is kernel.  The bare minimum is compiled ahead of time and the rest is compiled during boot.  The
    minimum is the file I/O and compiler.  Obviously, the module you boot must load the rest.  OSMain is what's loaded
    by the boot loaders.  It contains the ATA/ATAPI Port I/O, file system support, a scheduler and set-up to switch to
    32-bit and then 64-bit mode -- GDT, TR, multicore start-up and scheduling, memory management, etc.  I added
    some more to make debugging pleasant.   Instead of redundancy, I went ahead and made the OSMain the
    completed versions.  The reason I put the minimum into OSMain is I might add USB support so a boot could
    continue from a USB device and I would need to implement a full USB driver.  OSMain is loaded at address
    0x40000 and stretches to like 0x70000.  It must end before 0xA0000.  OSMain2 is the 64-bit compiler/assembler,
    keyboard and mouse, messaging and a simple editor.  The rest of the operating system is compiled during booting
    following the script /LT/OSMain/Adam1.APZ .  I decided that I wanted a syntax error in start-up scripts fixable, so I
    made a simple editor that is redundant, so theoretically you could fix an error.  In LoseThos you tinker with the
    start-up code and regularly render it unbootible.  In practice, I just boot to a second partition and use the editor to
    fix my main partition.  I so happens that OSMain and OSMain2 are about 40,000 lines of code together while the
    rest of the OS -- the graphic library, fancy editor, boot loader stuff and misc tools are another 40,000.
  • All functions are callable -- all symbols are retained.  OSMain and OSMain2 require compilation of extern function
    headers -- the remaining functions become instantly available as commands.  It's like you're living inside the
    compiler while it's running.  It compiles incrementally and once a function's been compiled, you can call it.  There's
    an index mechanism that groups and displays function names by category and there is a public flag that tells
    what's interesting, to distinguish from secondary functions.
  • Originally, my Tss structures were actually used as tss's, but in 64-bit mode Intel drastically changed them.  I have
    actual 64-bit tss's but they're not relevant for much because my task switching is done by hand and I just leave the
    real ones alone after setting them up.
  • Use "nounusedwarn var_name;" somewhere in a function to silence the unused variable warning.
  • The disk being accessed with port I/O is slower than DMA.  However, you should look at real world performance.  
    LoseThos has compressed files and is small.  If you use it for video games with low res graphics, file I/O will be the
    least of your worries.  LoseThos has a 32 Meg installed footprint.  My personal data boosts it to 50 Meg.  A disk
    cache of 128 Meg can fit everything.  Anything more than everything is waste.  I do make videos to export to
    Windows.  Why would one cache multimedia on a home system -- you don't generally watch stuff twice.  If you want
    to play with databases, good luck.  You can boost the cache size easily enough.
  • LoseThos is not limited to 4 Gig address space per task.  I mapped 128 Gig, real or not, and everybody can
    access it directly with pointers and/or the heap.  If you don't set-up a heap, you can just set a pointer to an
    absolute address and have-at it!  The heap objects are limited to 2 Gig each, so a raw pointer might be the way to
    go -- manage it yourself.  Virtual addresses map to physical and there are no protections, so you can access
    anything from each task.
